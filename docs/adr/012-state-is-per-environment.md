# 012. State is per environment, and belongs in its own cluster

**Status:** proposed — the backend is not chosen · **Scope:** platform · **Date:** 2026-08-09

## Context

State is a local file under `.tfstate/` today. That is adequate for one machine and one
cluster, and neither is true any more: [ADR 011](011-environments-are-clusters.md) makes an
environment a cluster of its own.

The intent is a Kubernetes backend — state kept as a Secret in the cluster it describes,
configured by Terragrunt — but the backend has not actually been settled, so this ADR is
`proposed` rather than `accepted`.

## Decision

**One state per environment.** Binding now.

**The backend is generated by Terragrunt in `root.hcl`, from `env.hcl`.** Binding now: the
backend and the provider read their target from the same place, so they cannot disagree
about which cluster is being addressed.

**Which backend is not settled.** Terraform's `kubernetes` backend, pointing at the same
cluster the provider addresses, is the intent. Until it is chosen, `.tfstate/` stays local
and gitignored.

## Rationale

- Per environment is not optional. One state spanning clusters would let a plan in one
  environment propose destroying another's resources — REQ-12 fails at the tooling layer
  before any workload is involved.
- **A Kubernetes backend is defensible here specifically because of
  [ADR 007](007-modules-receive-credentials.md).** State holds ApplicationSet specs and no
  credentials, so a Secret in that cluster's etcd exposes nothing that is not already in
  that same etcd. This reasoning does not transfer to a repo that keeps secrets in state,
  and should not be quoted as if it did.

## Consequences

- Chicken-and-egg, benign: planning an environment requires its cluster to be reachable.
  It already is — the cluster is a prerequisite this repo never creates. It does mean this
  repo can never grow into bootstrapping a cluster.
- Losing a cluster loses its state. Recoverable, because the state describes ApplicationSets
  and nothing unique; re-applying regenerates it. This would be unacceptable in a repo whose
  state held anything that could not be recomputed.
- Still to decide before this becomes `accepted`: whether the `kubernetes` backend's locking
  behaviour and object size limits are adequate here, and whether etcd encryption at rest is
  a precondition for adopting it.
